## 1. 目的

Backlog の指定プロジェクト・リポジトリ・プルリクエストに付いたレビューコメントを自動で読み込み、

1. 対応内容が明確なものはコード修正を行い、
2. 各コメントに対する回答コメントを投稿し、
3. コメント単位で対応状況を管理する。

コメント同士の繋がり（どのコメントへの返信か）が分かるコメントルールを定め、人間のレビュアーと Bot の双方がそれに従って運用する。

### 前提

- レビューコメントは**人間が自由記述で書く**ものを対象とする（定型フォーマットは前提にしない）。

## 2. Backlog API の制約（公式ドキュメントで確認済み）

| 事実 | 設計への影響 |
|---|---|
| PR コメントは**フラットな一覧**で、返信関係（親子）を表すフィールドがない | 繋がりは本文中のマーカーで表す（§4） |
| ドキュメントには位置情報の記載がないが、**実際のレスポンスには `filePath`・`position`・`oldBlobId`・`newBlobId` がある**（M0 で確認）。行コメントでは値が入り、場所を指定しないコメントでは `null` | 行コメントは `filePath` と `position` から場所を確定できる。`position` は**ファイル全体の差分での位置**で、ファイルの行番号ではない（§2-1）。場所のないコメントは本文から読み取るか推定する（§3-2）。ドキュメントにないフィールドのため、将来なくなる可能性も考え、`null` でも動くようにする |
| 取得は 1 回最大 100 件。`minId` / `maxId` / `order=asc` で範囲を指定できる | 前回処理した最大 ID から先だけを差分取得できる |
| PATCH で更新できるのは**認証ユーザー自身が投稿したコメントのみ** | Bot のサマリーコメントは上書きし続けられる（§4-5） |
| 「解決済み」の状態はない | 状態は自前で管理する（§4-4, §5） |
| PR に push したコミットは Web 画面には表示されるが、**コメントの一覧（API）には現れない**（2026-10-12 にテスト用 PR #3 で確認。修正のコミットを push した後の 21 件に、コミット由来のコメントや `changeLog` のあるコメントはなかった） | コミットメッセージが新しい指摘やスレッドの参照と取り違えられることはない。対策は不要 |

### 2-1. 行コメントの位置情報（M0 で確認）

| フィールド | 意味 |
|---|---|
| `filePath` | 対象ファイルのパス（リポジトリのルートから） |
| `oldBlobId` / `newBlobId` | 変更前 / 変更後のファイルの git blob ID。`git rev-parse origin/{base}:{filePath}` と一致することを確認 |
| `position` | **ファイル全体を 1 つの hunk にした差分**（`git diff -U99999` 相当）での行の位置。`@@` 行の次の行を 1 とし、`-`・`+`・変更なしの行をすべて数える |

- 画面上の差分は hunk ごとに区切られて表示されるが、`position` はその区切りと関係なく、**ファイル全体の差分**で数える
- 削除行か追加行かを示すフィールドはない。`position` が指す差分の行の種類（`-` / `+` / 変更なし）で判断する
- 場所を指定しないコメントでは、4 つのフィールドがすべて `null`

確認した実例（DEMO/demo-repo #3）:

| ファイル | 付けた行 | `position` | 備考 |
|---|---|---|---|
| `src/Code.ts` | 新 1 行目（差分の先頭行） | 1 | `@@` 行そのものは数えない |
| `src/Code.ts` | 旧 3 行目（`-` の行） | 3 | 削除行も数える |
| `src/Code.ts` | 新 3 行目（`+` の行） | 4 | 直前の削除行の分だけずれる |
| `src/Code.ts` | 新 21 行目 | 22 | |
| `src/Code.ts` | 新 28 行目（最終行） | 29 | |
| `src/backlog-api.ts` | 新 188 行目（画面上は 2 つ目の hunk） | 244 | 通常の `git diff`（前後 3 行）で数えると 86 になり一致しない。ファイル全体の差分で数えると 244 で一致 |

実装方針:

- 差分は `git diff -U{十分大きな数} {oldBlobId} {newBlobId}` で作り、`position` を次のどちらかに変換する
  - `+` か変更なしの行 → 新ファイルの行番号
  - `-` の行 → 旧ファイルの行番号（削除された行への指摘として扱う）
- 変換は CLI で行い、今回の実例をそのままテストケースにする
- 差分の取り方は、実例を確かめたときの git の既定（Myers・indent heuristic あり）に固定し、利用者の `~/.gitconfig` を読まない（2026-10-12 追加。敵対的レビュー R-9）。`diff.algorithm=histogram` などの設定で `-`・`+` の並びが変わり、行がずれるのを防ぐ
- 変換結果の行の内容を返信の「場所」に添え、ずれていたら人間が気づけるようにする
- 指摘の後にファイルが更新された（`newBlobId` と現在のブランチの blob が違う）場合は、指摘時点のファイルと現在のファイルの差分で行番号を追いかける。指摘された行そのものが変更されていれば「行は変更済み」とする（M5 で、修正した行の場所が分からなくなる問題が見つかったため）

まだ確認していないこと:

- Backlog の差分アルゴリズムが `git diff` の既定（Myers）と一致するか。変更の並び方があいまいな箇所（同じ行が繰り返される場合など）では、`-` と `+` の並びが変わり、`position` がずれる可能性がある。今回の 6 件では一致した
  - 対策: 変換した行の内容がコメントの本文と明らかに無関係なら、場所の判定を `inferred_multiple` 相当に下げる（§3-3）

使用する API:

- `GET  /api/v2/users/myself`（認証ユーザーの ID を取得。Bot の返信の判定に使う → §4-6）
- `GET  /api/v2/projects/:projectIdOrKey/git/repositories/:repoIdOrName/pullRequests/:number`
- `GET  /api/v2/projects/:projectIdOrKey/git/repositories/:repoIdOrName/pullRequests/:number/comments`
- `POST /api/v2/projects/:projectIdOrKey/git/repositories/:repoIdOrName/pullRequests/:number/comments`（`content`）
- `PATCH /api/v2/projects/:projectIdOrKey/git/repositories/:repoIdOrName/pullRequests/:number/comments/:commentId`（`content`）

## 3. 構成と処理フロー

### 3-1. 構成

**決まった処理は TypeScript の CLI、判断と修正は Claude Code のスキル**が担当する。

```
backlog-fix-review-comments/
├─ docs/plan.md                   # 本ファイル
├─ src/                           # TS CLI（同じ入力なら毎回同じ結果になる処理）
│   ├─ backlog/client.ts          # API 呼び出し（ページング・レート制限・リトライ）
│   ├─ backlog/url.ts             # PR の URL の解析（API キーの送り先の制限）
│   ├─ git/diff.ts                # position → 行番号の変換（§2-1）、変更ファイルと変更行の範囲
│   ├─ thread/marker.ts           # マーカー・RC- 参照の解析と生成（§4）
│   ├─ thread/thread.ts           # スレッドの組み立てと状態の算出（§4-4, §4-6）
│   ├─ interpret/interpretation.ts # 解釈の検証とランクの規則（§3-3）
│   ├─ reply/format.ts            # 返信とサマリーの書式（§4-3, §4-5）
│   ├─ state/store.ts             # ローカルの状態ファイル（§5）
│   ├─ sync.ts                    # 起動時の同期とスナップショット（§5-1）
│   ├─ commands.ts                # 各サブコマンドの処理
│   └─ cli.ts                     # fetch / status / interpret / reply / summary（と M0 の probe）
├─ test/fixtures/                 # テスト用 PR の実データ（個人を特定できる情報は架空の値に置き換え済み）
└─ skill/backlog-fix-review/      # 配布物（§7-A）。scripts/ は src/ からビルドする
```

CLI のサブコマンド:

| コマンド | 処理 | 手順 |
|---|---|---|
| `fetch <URL>` | 同期して未対応の指摘を表示し、スナップショット（JSON）を保存する | §3-2 手順 1 |
| `status <URL>` | 同期してすべての指摘の状態を表示する | |
| `interpret <URL> --file <json>` | Claude の解釈を検証し、ランクを決めて保存し、確認①の一覧を表示する | §3-2 手順 2〜4 |
| `select <URL> --choice <1,3-5 / all / none>` | 確認①の利用者の回答を、指摘の番号と扱い（修正・質問・回答・見送り）に置き換えて表示する（2026-10-12 追加） | §3-2 手順 4 |
| `commit <URL> --key --message-file` | ステージした変更を、指摘 1 件の修正としてコミットする。`Refs: RC-{id}` を付け、修正の対象の指摘か・PR のブランチの上か・ファイルが論点の場所と合うかを確かめる（2026-10-12 追加） | §3-2 手順 5 |
| `reply <URL> --key --status --body-file [--commit]... [--yes]` | 返信する。`--yes` がなければ下書きを表示するだけ | §3-2 手順 7 |
| `reply <URL> --batch <json> [--yes]` | 複数の返信をまとめて扱う。同期は 1 回。下書きを一度に表示し、`--yes` なら順に投稿する（2026-10-12 追加） | §3-2 手順 6・7 |
| `summary <URL> [--yes]` | サマリーを作成または更新する。`--yes` がなければ下書きを表示するだけ | §4-5 |

`reply` が拒否するもの（スキルの手順を誤っても壊れないようにするため）:

- 未対応（`open`）でない指摘への返信（再実行による二重返信を防ぐ）
- 種類 `fix`・ランク `high` 以外の指摘を `fixed` にすること（§7-4）
- 論点の組み合わせから決まる状態（§3-3「返信の状態」）と違う状態での返信（2026-10-12 追加, §7-8）
- コミットのない `fixed`、PR のブランチ（`origin/{branch}`）に含まれていないコミット（push 前の投稿を防ぐ）。下書き（`--yes` なし）は確認②のため push 前に作るので、警告を出すだけにする
- メッセージにその指摘の `Refs: RC-{id}` がないコミットを付けた `fixed`（2026-10-12 追加。敵対的レビュー R-4）。別の指摘のコミットや、PR の作成者が元から積んでいたコミットの取り違えを防ぐ。下書きでも拒否する（push 前ならメッセージを直せるため）
  - コミットが論点の場所（`location.path`）・仕様書（`scope.docs`）・行コメントのファイルのどれも変更していなければ、警告を出す（テストだけを直す修正もありうるので拒否はしない）
  - 「解釈した時点より後のコミットか」は確かめない。解釈した時点のブランチの位置を状態ファイルに持つ必要があり、環境を変えると働かないため

- **CLI**: コメントと差分の取得、スレッドの組み立て、未対応一覧の JSON 出力、返信の投稿、サマリーの更新
- **スキル**: コメントの解釈と分類、コード修正、テスト実行、返信文の作成、人間への確認

### 3-2. 処理フロー

0. **起動と対象 PR の確定**
   - 引数で PR の URL を受け取る（`/backlog-fix-review <PR URL>`）
   - URL が渡されていない場合は、スキル内でユーザーに PR の URL を尋ね、回答を待つ。推測で補ったり、以前の PR を勝手に使ったりしない
   - URL が不正な形式なら、理由を示してもう一度尋ねる
1. **取得と同期**: PR 情報、コメント全件、`git diff origin/{base}...origin/{branch}` を取得し、ローカルの JSON を Backlog に合わせて更新する（§5-1）。そのうえでスレッドを組み立てる
2. **解釈**: 未対応コメント 1 件ごとに、Claude が次の項目を出す（詳細は §3-3）
   - 解釈の前に、その指摘の**会話の履歴**（元のコメント・レビュアーの追加の指示や回答・Bot の返信）を読み、前回 Bot が何を質問・回答したかを踏まえる（§5-1 の 5, 2026-10-12 追加）
   - 解釈が必要な指摘には、CLI が**周りのコード**（`context`）をスナップショットに入れる（2026-10-12 追加。改善案 A-1）。Claude はまずこれを読み、影響範囲が広い可能性があるときだけファイル全体や差分を読む
     - 行コメント: 指摘された行の前後 15 行（行番号つき）と、その行を含む PR の差分の hunk。行は blob から切り出す（削除行なら変更前、指摘の後にファイルが更新されていれば現在のファイルの `currentLine`）
     - 本文（最新の追加の指示、なければ元のコメント）の `📍 path L42`: CLI が書式どおりに読み取って同じように切り出し、「本文から読んだ場所」と印を付ける。場所の判定は Claude が行う
     - 場所の手がかりがない指摘には入れない。1 件の指摘に入れるのは 3 か所まで、hunk は 60 行まで
   - **場所**: パスと行番号、および場所の判定（`explicit` など）とその根拠
   - **種類**: `fix` / `answer` / `needs_info` / `wontfix` / `not_actionable`
   - **意図**・**影響範囲**の判定とその根拠
   - **修正方針**: 一言で
   - 1 つのコメントに複数の論点があっても**分割しない**。1 件の解釈の中に論点（`points[]`）として並べ、論点ごとに上の項目を出す（2026-10-12 決定, §7-8）。状態の管理は常に「1 コメント = 1 指摘」
   - **Claude は確信度のランクを自分で付けない**。ランクは CLI が判定結果から規則で決める（§3-3）
3. **振り分けの規則**
   - 指摘全体のランクと返信の状態は、論点の組み合わせから CLI が決める（§3-3「論点と指摘全体」）
   - 指摘全体のランクが `high`（`fix` の論点がすべて `high` で、利用者の判断が要る論点がない）のものだけを自動修正の候補にする（§7-4）
   - 利用者の判断が要る論点が 1 つでもあれば、**どの論点も直さず**、`needs_info` として確認の質問を返す（推測で直さない）。質問には、ランクが下がった理由（候補が複数ある、影響範囲が広い、など）と、**直し方が決まっている論点の方針**（「回答をいただいたらまとめて直します」）を書く
   - レビュアーが回答すると指摘は `open` に戻り、回答を踏まえて**すべての論点を解釈し直す**。すべての直し方が決まった時点で、まとめて直す
4. **人間の確認①**: 解釈結果の一覧を、ランクと判定の根拠つきで見せ、対応するものを選んでもらう（`1,3-5` / `all` / `none` の形式）。回答は CLI の `select` に渡し、番号を指摘に置き換える（エージェントが一覧を見て置き換えない。2026-10-12 追加）。選べるのは自動修正の候補（`high`）と、返信だけのもの（`answer` / `needs_info` / `wontfix`）
   - 意図ははっきりしているが、直し方の細部に選択肢がある場合（例: 新しい関数を置くファイル）は、ランクは変えずに、確認①でその選択肢を示して利用者に選んでもらう（M5 で採用）
   - 仕様書の更新を伴う指摘（影響範囲が `local_with_docs`、§3-3）は、ランク `mid` のまま「利用者が選べば修正」として示し、直す仕様書のパスも見せる。利用者が選んだものだけを修正する（§7-4 の例外）
   - PR で規約のファイル（§3-4）が変更されていれば、そのことを知らせる
5. **修正**: feature branch で作業し、**コメント 1 件ごとに 1 コミット**にする（コミットメッセージに `Refs: RC-{id}`）。コミットは CLI の `commit` で行う（2026-10-12 追加。改善案 A-5）。論点が複数あっても、すべての論点の修正を同じ 1 コミットに含める（§7-8）。lint・テストを実行する
   - 修正の前に、対象リポジトリの規約を読み、そのやり方に沿って直す（§3-4）
   - 仕様書の更新を伴う指摘では、仕様書の更新も**同じコミット**に含める
6. **人間の確認②**: 差分と返信文を見せてから、push と投稿を行う
   - lint・テスト・型チェックなど修正を検証する手段がなかった、または実行できなかった場合は、何で検証したか（差分の確認だけ、など）を必ず報告する（M5 で採用）
7. **投稿**: 各コメントへの返信と、サマリーコメントの更新

### 3-3. 解釈の判定とランク

確信度を Claude の自己申告にすると、基準があいまいで実行ごとにぶれ、人間も検証できない。そこで **Claude には事実の判定と根拠だけを出させ、ランクは CLI が規則で決める**。

**Claude が出す判定**（それぞれに根拠を 1 文で付ける）

| 項目 | 値 | 意味 | 根拠の例 |
|---|---|---|---|
| 場所 | `explicit` | 本文にパスと行番号が明記されている | 「`📍 src/order/service.ts L42` と記載」 |
| | `inferred_unique` | 本文にはないが、差分内で候補が 1 つに絞れる | 「`createOrder` は差分内で service.ts L42 のみ」 |
| | `inferred_multiple` | 差分内に候補が複数ある | 「`tmp` は差分内に 3 箇所」 |
| | `unknown` | 候補が見つからない | |
| 意図 | `clear` | 期待する結果が書かれている、または直し方が 1 通り | 「『ログ出力して再スロー』と明記」 |
| | `ambiguous` | 直し方が複数ある、または何を求めているか読み取れない | 「『もう少し良い名前に』のみ」 |
| 影響範囲 | `local` | 指摘された箇所だけの変更で済む | |
| | `local_with_docs` | コードの変更は指摘された箇所だけだが、仕様書（requirements.md・design.md など）の記述も合わせて直す必要がある。直す仕様書のパスを `scope.docs` に書く（2026-10-12 追加） | 「design.md の 3.2 節にある関数名も変わる」 |
| | `wide` | 複数ファイルの変更や設計の変更が必要 | |

**CLI がランクを決める規則**（`fix` のみに適用）

| ランク | 条件 |
|---|---|
| `high` | 場所が `explicit` か `inferred_unique`、かつ意図が `clear`、かつ影響範囲が `local` |
| `low` | 場所が `unknown`、または意図が `ambiguous` |
| `mid` | それ以外（場所が `inferred_multiple`、または影響範囲が `wide` か `local_with_docs`） |

- **例外**: `mid` になった理由が「仕様書の更新が必要」（影響範囲が `local_with_docs`）**だけ**なら、「利用者が選べば修正」として扱う。確認①で利用者が選んだときだけ修正し、`fixed` で返信できる。選ばなければ、ほかの `mid` と同じく確認の質問を返す（2026-10-12 決定, §7-4）
- ランクの決め方は CLI のコードとテストで固定する。規則を変えるときは、先にこの表を更新する
- **CLI が照合する事実**（2026-10-12 追加。敵対的レビュー R-5）: 判定はエージェントの自己申告なので、機械で確かめられることは CLI が確かめる。ランクは変えない（不一致でランクを下げると、利用者の判断で済むことがレビュアーへの質問に変わるため）
  - 拒否: `location.path`・`scope.docs` がリポジトリの中の相対パスでない（絶対パス・`..`・`\`）。`location.line` が、PR のブランチ（なければ base）のそのファイルの行数を超えている
  - 確認①で警告: 行コメントなのに、どの論点もそのファイルを指していない。`location.path` が PR の変更ファイルにない（範囲外のファイルに置く案は、確認①で利用者が選ぶ運用のため警告にとどめる）。ファイルが PR のブランチにも base にもない
  - 確認①に元のコメントの全文（と最新の追加の指示）を出す。論点を `points` に書かずに落としていないかを、利用者が見比べられるようにする
- 判定と根拠は確認①に表示し、ローカルの JSON にも保存する（§5）

**論点と指摘全体**（2026-10-12 追加, §7-8）

1 つのコメントに複数の論点があっても分割せず、1 件の指摘として扱う。判定（種類・場所・意図・影響範囲）と上の表のランクは**論点ごと**に出し、指摘全体の扱いは CLI が論点の組み合わせから決める。

- **指摘全体のランク**: `fix` の論点のランクのうち、いちばん低いもの。`fix` の論点がなければ付けない
- **「利用者が選べば修正」の例外**: `high` でない `fix` の論点がすべて「仕様書の更新だけが理由の `mid`」で、ほかに利用者の判断が要る論点がなければ、指摘全体を「利用者が選べば修正」にする。確認①で選ばれたら、その論点を `high` と同じに扱う
- **返信の状態**: 上から順に、最初に当てはまるもの。CLI はこの状態以外での返信を拒否する

| 論点の組み合わせ | 返信の状態 | 修正 |
|---|---|---|
| 利用者の判断が要る論点（`high` でない `fix`、`needs_info`）が 1 つでもある | `needs_info` | しない。決まっている論点の方針も返信に書く |
| `wontfix` の論点があり、ほかに `fix` か `answer` の論点もある | `needs_info` | しない。見送ってよいかを聞く |
| `fix` の論点がある（すべて `high`） | `fixed` | すべての論点を 1 コミットで直す。`answer` の論点の回答も同じ返信に書く |
| `wontfix` の論点だけ（`not_actionable` を除く） | `wontfix` | しない（見送りは利用者の同意が必要） |
| `answer` の論点だけ（`not_actionable` を除く） | `answered` | しない |
| すべて `not_actionable` | 返信しない | しない |

- 論点が 1 つだけなら、これまでの 1 件の判定と同じ結果になる
- 確認①で選ぶ単位は指摘（コメント）。論点ごとには選ばない
- 一部の論点だけ先に直すことはしない。すぐ直せる論点も回答を待つので 1 往復遅れるが、回答で前提が変わることもあるため、すべての方針が決まってから直す。急ぐ論点は、レビュアーにコメントを分けてもらう

### 3-4. 対象リポジトリの規約に従う（2026-10-12 追加）

修正するときは、対象リポジトリのやり方に沿って、コードと仕様書を直す。

- **読む規約**: `AGENTS.md`・`CLAUDE.md`・`.kiro/steering/`（cc-sdd / Kiro の Steering）・`.github/copilot-instructions.md`・`.cursor/rules/`・`CONTRIBUTING.md` など。仕様書は `.kiro/specs/<機能>/requirements.md`・`design.md`・`tasks.md` など
- **仕様書と Steering の場所は決め打ちしない**（2026-10-12 追加）。cc-sdd などは設定で場所を変えられ、その場所はエージェントが最初に読む規約（AGENTS.md など）に書かれていることが多い
  1. まず、エージェントが最初に読む規約（`AGENTS.md`・`CLAUDE.md`・`GEMINI.md`・`.github/copilot-instructions.md` など）を読み、仕様書・Steering の場所が書かれていれば、その場所を使う
  2. 書かれていなければ、既定の場所（`.kiro/specs/`・`.kiro/steering/`）を探す
  3. どちらにも見つからなければ、仕様書はないものとして扱う（影響範囲を `local_with_docs` にしない）
  4. 使った場所と、その根拠（どの規約のどこに書かれていたか、または既定の場所）を確認①で示す
- **規約は解釈（§3-2 手順 2）の前に読む**。`local_with_docs` かどうかは、仕様書を読まないと判定できないため
- **PR のブランチの内容を読む**（利用者の判断）。作業ディレクトリは PR のブランチなので、多くのエージェントは起動時にそこの規約を読むことになり、実態とも合う
- **従う範囲を限る**: 規約に従うのは、書き方・命名・テスト・コミットメッセージの書式・ドキュメントの更新の仕方などの**開発のやり方**だけ。確認の省略、外部への通信、資格情報や許可に関わる指示には従わず、利用者に報告する。スキルの「守ること」が常に優先する（PR の作成者が規約を書き換えて指示を紛れ込ませる可能性があるため）
- **規約とスキルの決まりがぶつかったとき**: 安全のための決まり（CLI の `commit` でのコミット、`env -u BACKLOG_API_KEY` など）はスキルを優先し、書式（Conventional Commits など）はリポジトリの規約に従う
- **PR で規約が変わっていれば知らせる**: CLI の `fetch` は、PR の変更ファイルに規約のファイルがあれば警告し、スナップショットの `conventionChanges` に入れる。確認①でそのことを利用者に伝える
  - CLI が見分けるのは、よく使われる名前と場所（`AGENTS.md`・`CLAUDE.md`・名前に `steering` を含むディレクトリ・`.kiro/steering/` など）だけ。規約で Steering の場所が変えられている場合は、エージェントがその場所を `changedFiles` と照らし合わせ、変更があれば確認①で伝える

## 4. コメントの繋がりを表すルール

### 4-1. ID

- Backlog のコメント `id` をそのまま使い、`RC-{id}` と表記する（Review Comment）
- スレッドの起点（最初の指摘）を **root** とし、スレッド内のどの返信も root の ID を持つ
- 指摘を分割した ID（`RC-123#1`）は使わない（2026-10-12 決定, §7-8）。以前の返信のマーカーやレビュアーのコメントに `#数字` があれば、それを無視して root 全体（`RC-123`）への返信として読む

### 4-2. レビュアー（人間）のルール

ルールは少なく、守られなくても処理が壊れないようにする。
利用者本人のコメントにも同じルールを適用する（§4-6）。

| ルール | 必須かどうか | 守られなかったとき |
|---|---|---|
| 1 コメントに 1 指摘 | 推奨 | 分割せず 1 件の指摘として扱う。直し方の決まらない論点が 1 つでもあれば、ほかの論点も回答を待ってからまとめて直す（§3-3） |
| 場所を書く: `📍 src/foo.ts L42` | 推奨 | Claude が推定し、分からなければ聞き返す |
| 再指摘や返信は先頭に `RC-123` を書く | **必須** | 新しいスレッドとして扱われる |
| 解決したら `RC-123 ✅` と書く | **必須** | `fixed` のまま残り、サマリーで「確認待ち」と表示される |
| 対応不要にするときも `RC-123 ✅ 対応不要` と書く | **必須** | 解決と同じく `resolved` になる（2026-10-12 決定。取り下げ用の別の状態は作らない） |

- 解決の印は `✅` のほか、`✔`・`✔️`・`☑`・`☑️`・`✓` と、絵文字の記法 `:white_check_mark:`・`:heavy_check_mark:`・`:ballot_box_with_check:` も受け付ける（2026-10-12 追加。敵対的レビュー R-6 の一部）。以前は `RC-123 ✔` が解決ではなく再指摘として扱われ、指摘が open に戻っていた。「済」などの言葉は、「済みではない」のような文と区別できないので印にしない
- 番号の書き方の揺れも吸収する（2026-10-12 追加。R-6）。最初の行を NFKC で正規化し（全角の英数字と記号を半角に）、ハイフンに似た文字（`‐`・`–`・`−` と長音の `ー` など）を `-` にそろえ、大文字小文字を区別しない。以前は `ＲＣ－123` などが新しい指摘として扱われ、自動修正の対象になりえた。外部のコマンドやパッケージは使わず、Node.js の標準機能だけで行う。読み取りのためだけにそろえ、コメントの本文は変えない
- 引用は番号と印の**後**に書く。先頭の引用ブロックは読み飛ばさない（2026-10-12 利用者の判断）。番号は最初の行だけから読むので、引用の中の `RC-123 ✅` を参照や解決と取り違えない。引用から書き始めた返信は新しい指摘として扱われるが、確認①の一覧に出るので、黙って自動修正されることはない

任意で使えるテンプレート:

```
📍 src/order/service.ts L42
指摘: 例外を握りつぶしている
期待: ログ出力して再スロー
```

### 4-3. Bot の返信フォーマット

```
🤖 自動対応 ↩️ RC-12345 への返信（tanaka さん）
> 例外を握りつぶしている…

**状態**: ✅ 対応済み
**場所**: `src/order/service.ts` L42（推定）
**対応内容**: catch 内で logger.error を呼び、再スローするよう修正しました。
**コミット**: abc1234

`[review-bot root=12345 reply-to=12345 status=fixed]`
```

- 1 行目と最後の行は、人間にも読めて機械でも確実に解析できる形にする
- 個人アカウントで投稿するため、1 行目に必ず「🤖 自動対応」を付け、本人の手書きコメントではないことが分かるようにする
- 相手の名前に `@` は付けない（Backlog のメンション記法 `@ユーザーID` と紛らわしく、意図しない通知を避けるため）
- 場所を Bot が推定した場合は「（推定）」と明記する
- `needs_info` の返信には、何を答えてほしいかを具体的に書く。論点が複数あれば、直し方が決まっている論点の方針（回答後にまとめて直すこと）も書く（§3-3）
- 返信・サマリーは**マークダウン記法**で書く（§7-5）
- M0 で表示を確認した結果（#5725744）: 絵文字・引用・太字・インラインコード・表は期待どおりに表示される。**`<!-- -->` は画面に表示されない**。API で取得すると本文はそのまま返り、HTML コメントも残っている
- マーカーは**見える形**（`` `[review-bot ...]` ``）のままにする（§7-7）

マーカーの書式:

```
[review-bot root={rootId} reply-to={parentId} status={status}]
[review-bot summary]
```

### 4-4. 状態の移り変わり

```
open → fixed / answered / needs_info / wontfix / not_actionable
  ↑ レビュアーが RC-xxx で返信                    ↓ レビュアーの RC-xxx ✅
  └───────────────────────────────────────── resolved
```

- スレッドの状態は「最後のコメントが Bot のものか人間のものか」と、そのマーカーの `status` から決める
- `needs_info` や `fixed` に対してレビュアーが（✅ 以外で）返信すると `open` に戻る
- `not_actionable`（「LGTM」など）には返信せず、サマリーにも出さない。返信がないので、この判定だけはローカルの解釈から求める（ローカルの状態が消えると `open` に戻り、解釈し直しになる）
- Bot の返信の後に root が編集された場合は、自動では `open` に戻さず、警告を出して人間に確認を促す

### 4-5. サマリーコメント

PR 内に Bot のコメントを 1 件だけ置き、PATCH で更新し続ける。

```
## 🤖 レビュー対応状況（最終更新: 2026-10-10 23:40）

進み具合: ☑️ 完了 0 / 3 件（レビュアーの確認待ち 2 件・自動対応待ち 1 件）

| RC | 指摘者 | 要約 | 状態 | 場所 | コミット | 最新の返信 |
|----|--------|------|------|------|----------|------------|
| [RC-12345](#comment-12345) | tanaka | 例外処理 | ✅ fixed | `src/order/service.ts` L42 | abc1234 | [#12360](#comment-12360) |
| [RC-12350](#comment-12350) | suzuki | 命名 | ❓ needs_info | 不明 | - | [#12361](#comment-12361) |
| [RC-12370](#comment-12370) | suzuki | 例外処理 | ⏳ open | 不明 | - | - |

**📝 次にすること**（すべての指摘が ☑️ resolved になれば完了です。番号は上の表の RC 列。コメントの**先頭**に書く）
- ⏳ open → 自動対応を待つ（レビュアーは何もしなくてよい）
- ✅ fixed → 確認して問題なければ `RC-番号 ✅`、直っていなければ `RC-番号 理由`
- ❓ needs_info → `RC-番号 回答` で答える
- 💬 answered / 🙅 wontfix → 納得なら `RC-番号 ✅`、そうでなければ `RC-番号 理由`
- ☑️ resolved → 完了（何もしなくてよい）
- 対応不要にする → `RC-番号 ✅ 対応不要`
- 新しく指摘する → 行コメントで付ける（または `📍 ファイル L行`）。1 コメントに 1 指摘

`[review-bot summary]`
```

- **進み具合の 1 行と、状態ごとの「次にすること」を載せる**（2026-10-12 追加。案 C の改良版）。レビュー指摘をすべて完了（resolved）に持っていくため、表の状態を見れば、次に誰が何をすればよいかが分かるようにする
  - 進み具合: 完了 = `resolved`、レビュアーの確認待ち = `fixed`・`answered`・`wontfix`・`needs_info`、自動対応待ち = `open`。件数は `not_actionable` を除いて数える
  - 「次にすること」は表の後、マーカーの行の前に置く（マーカーは最後の行でないと働かないため, §6-1）。指摘が 0 件のときも、新しく指摘するときの書き方のために載せる
  - Backlog は折りたたみ（`<details>`）を使えないので、短く保つ
  - テスト用 PR #3 のサマリー（#5725764）で、進み具合・表・次にすることの表示を利用者が画面で確認した（2026-10-12）

- **人間が該当するコメントをすぐ開けるよう、RC 列と「最新の返信」列をコメントへのリンクにする**（2026-10-12 追加）
  - コメントへのリンクの形は `https://{space}/git/{PROJECT}/{repo}/pullRequests/{N}#comment-{コメント ID}`（利用者が画面で確認。行コメントでも同じ形でそのコメントに飛べる）
  - **サマリーでは、ページ内のリンク `#comment-{コメント ID}` だけを使う**（2026-10-12 変更）。サマリーは同じ PR の画面にあるので、ページ内で移動できる。完全な URL だと外部リンクとして新しいタブが開き、煩わしいため
  - 画面で確認した結果（2026-10-12）: Backlog はページ内のリンクでも必ず新しいタブで開く仕様だった。新しいタブが開くのは避けられないが、利用者の判断で、ページ内のリンクの形のまま採用する
  - RC 列は元の指摘へのリンク
  - 「最新の返信」列は、その指摘への最後の自動返信へのリンク。返信がまだなければ `-`
  - リンク先は、CLI が検証したコメント ID（正の整数）だけから作る。レビュアーが書いた文は使わないので、引用文のリンクを無効にする対策（§6-1, S-3）とはぶつからない。ID が正の整数でなければリンクにしない
- 指摘者の名前には `@` を付けない（§4-3 と同じ理由）

### 4-6. 投稿者によるコメントの分類

Bot は利用者の**個人アカウント**で投稿する（§7-2）。そのため、投稿者 ID だけでは Bot の返信と本人の手書きコメントを区別できない。起動時に `GET /api/v2/users/myself` で自分の ID を取得し、次のように分類する。

| 投稿者 | マーカー | 扱い |
|---|---|---|
| 自分 | あり | **Bot の返信**。マーカーの `status` を状態に反映する。対応の対象にはしない |
| 自分 | なし | **通常のレビューコメント**。他のレビュアーと同じく §4-2 のルールで解釈し、修正の対象に含める |
| 他人 | あり | **なりすましの可能性があるためマーカーを無視**し、通常のレビューコメントとして扱う |
| 他人 | なし | 通常のレビューコメント（§4-2 のルールで解釈する） |

- 利用者本人もレビュアーの 1 人として扱う。本人が付けた指摘も自動修正の対象になる
- 本人が手動で対応を済ませた場合も、他のレビュアーと同じく `RC-123 ✅` で解決にする
- 本人が `RC-123` で始まるコメント（✅ なし）を書いた場合は、追加の指示や再指摘として扱い、スレッドを `open` に戻す
- 無限ループは「自分の ID ＋マーカーあり」を対象外にすることで防ぐ。そのため、Bot の返信からマーカーを消すと、その返信が新しい指摘として扱われる点に注意する
- **1 つの PR は、同じ人のアカウントでだけ対応する**（2026-10-12 利用者の判断）。別の人が引き継ぐと、前の担当者の自動返信が「他人＋マーカーあり」になり、新しい指摘として扱われ、返信済みの指摘が open に戻り、サマリーも 2 つになる。引き継ぎは当面必要ないので、他人のマーカーを無視する今の決まりのままにする
- なりすましへの備えは、閉じた開発者のチームで運用する前提では過度に気にしなくてよい（コメントには投稿者が残る）。今の決まりを保つのは、上の前提を単純に保つためでもある

## 5. 状態をどこに持つか

- **正は Backlog のコメント本文のマーカー**。ローカルの状態が消えても、コメントを全件読み直せば同じ状態に戻せる
- ローカルの JSON（`.review-state/{PROJ}-{repo}-pr{N}.json`）はキャッシュとして使い、次のものを持つ。置き場所は、**スキルを起動したディレクトリのリポジトリのルート**（`git rev-parse --show-toplevel`）の下の `.review-state/` とする（2026-10-11 利用者の指示）。worktree で起動した場合は、その worktree のルートになる。スナップショット（`{...}.snapshot.json`）も同じ場所に置く
  - `.review-state/` は対象リポジトリでは追跡されないファイルになる。スキルはコミットに含めない（`git add` はファイルを指定して行う）
  - `.review-state/` を `.gitignore` や `.git/info/exclude` で無視させることはしない（2026-10-11 利用者の判断）。指摘対応の記録として、後で整形して使う可能性があるため
  - 差分取得用の `lastCommentId`
  - Claude の解釈結果（場所・種類・判定と根拠）と、CLI が決めたランク。再解釈によるぶれとコストを防ぐため
  - コメントとコミットの対応、処理ログ

### 5-1. 起動時の同期

スキルの起動時には、まずローカルの JSON を Backlog に合わせて更新する。

1. **コメントを全件取り直し、スレッドと状態を作り直す**
   - `minId` による差分取得だけでは、古いコメントの編集や、前回の実行が途中で止まったことによるずれを取りこぼすため
   - `lastCommentId` による差分取得は、取得を速くするための工夫にとどめる
2. **解釈結果は「コメント ID ＋ `updated`」をキーに残す**
   - `updated` が変わっていなければ前回の解釈を使い、変わっていれば解釈し直す
3. **ローカルと Backlog が食い違ったら、常に Backlog の内容を正とする**
4. **返信を 1 件投稿するたびに、すぐ JSON へ書き込む**
   - 途中で止まっても、次の起動時の作り直しで正しい状態に戻る
5. **指摘ごとの会話の履歴を、Backlog のコメントだけから作ってスナップショットに入れる**（2026-10-12 追加。敵対的レビュー R-7）
   - レビュアーが回答すると前回の解釈は期限切れになり、Bot の返信の本文もスナップショットになかったため、エージェントは何を質問したか分からないまま解釈し直していた。これは `.review-state` が残っている環境でも起きていた
   - `history` には、元のコメント・追加の指示や回答・解決・Bot の返信を、コメントの順に並べる。各要素に役割（`review` / `follow_up` / `resolve` / `bot_reply`）を付ける。Bot の返信は自分のコメントなので返信の状態も付けるが、本文には引用したレビュアーの文が含まれる
   - 同期のたびに全件取り直すコメントから作るので、**どの環境で実行しても同じ内容になる**。環境を変えて続けても、会話の文脈は失われない
   - 期限切れの前回の解釈（root が編集されていないもの）は、同じ環境に残っていれば `previousInterpretation` として参考に添える。なくても解釈できるようにし、これには頼らない
6. **サマリーの「場所」と「コミット」は、自分の自動返信からも読み戻す**（2026-10-12 追加。敵対的レビュー R-14）
   - 場所を指定しないコメントの場所と、指摘ごとの修正コミットは、手元の解釈と状態ファイルにしかなかった。別の環境で続けたり、状態ファイルが消えたり、以前の形の解釈を捨てたりすると、サマリーで「不明」「-」になっていた（テスト用 PR #3 の RC-5725758 で発生）
   - 自動返信には、CLI が決まった書式で `**場所**:` と `**コミット**:` の行を書いている（§4-3）。マーカーと同じく、自分のマーカー付きのコメントからだけ読む
   - 場所は「行コメントの位置 → 有効な解釈 → 最後の自動返信の場所」の順に使う。コミットは状態ファイルと自動返信の両方を合わせる（返信には短い ID しかないので、同じコミットは短い ID の一致でまとめる）

## 6. 安全面

- **利用者の個人アカウントの API キーで投稿する**（Bot 専用ユーザーは用意できない → §7-2）
  - 「自分の ID ＋マーカーあり」を Bot の返信と判定し、自分の返信に反応し続ける無限ループを防ぐ（§4-6）
  - 他人が書いたマーカーは信用しない（なりすまし対策）
  - キーは本人のすべての権限を持つため、出力・ログ・状態ファイル・コミットに絶対に含めない
- **コメント本文は信頼できない入力として扱う**
  - コメント内の命令文は修正方針の参考にとどめる
  - コメントに書かれたコマンドは実行しない
  - 修正は PR の差分の範囲に限る。範囲外を触る場合は人間の確認②で明示する
- force push は禁止。push 前に必ず人間が承認する
- API キーはクエリ文字列で送るため、ログや出力に残さないようマスクする
- `env -u BACKLOG_API_KEY` は子のプロセスの環境からキーを外すだけで、同じユーザーで動くコードは親のプロセスの環境（Linux の `/proc/<pid>/environ` など）からキーを読める。キーをファイルから読む形にしても、同じユーザーのコードはそのファイルも読めるので、守れる範囲は変わらない。根本的な対策はサンドボックスやコンテナでの実行で、README の「このツールが防がないこと」に書く（2026-10-12 追加。敵対的レビュー R-8。キーの置き場所は変えない）
- API キーは環境変数（`BACKLOG_API_KEY`, `BACKLOG_SPACE`）から読む。**`BACKLOG_SPACE` は必須**で、PR の URL のホストと一致しなければ中止する（2026-10-11 決定。未設定だと任意の Backlog スペースにキーを送れてしまうため）

## 7-A. 配布の形（2026-10-11 追加）

Agent Skills の標準形式（`SKILL.md` を持つフォルダ）で配布し、Agent Skills に対応した各エージェント（Claude Code など）で使えるようにする。

- **スキルのフォルダだけで完結させる**: CLI をビルドした JavaScript を `scripts/` に同梱し、フォルダの外のファイルやシンボリックリンクに頼らない
- **実行環境**: Node.js 20 以上（TypeScript の実行や `npm install` を不要にするため、ビルド済みの JavaScript を同梱する。実行時の依存パッケージはない）と git
- **特定のエージェントに依存しない書き方**: `SKILL.md` は「エージェント」に向けて書き、Claude Code 固有の設定は README の該当節に分ける
- **段階的な読み込み**: `SKILL.md` は手順の本体だけにし、判定の定義やレビュアー向けのルールは `references/` に分ける

```
skill/backlog-fix-review/        # 配布物（このフォルダをそのまま配る）
├─ SKILL.md                      # frontmatter（name, description, compatibility, license, metadata）と手順
├─ README.md                     # 利用者向けの短い案内（必要なもの・導入・使い方・守ること）。数分で読める長さに保つ
├─ references/
│   ├─ details.md                # 利用者向けの詳細（許可設定・セキュリティ・作成されるファイル・CLI・トラブルシューティング）
│   ├─ interpretation.md         # 解釈の JSON と判定の定義（手順 2 で読む）
│   └─ reviewer-guide.md         # レビュアーに共有するルール
└─ scripts/                      # `npm run build` で src/ から生成する（直接編集しない）
    └─ cli.js ほか
```

- 開発用のファイル（`src/`、テスト、`docs/plan.md`）は配布物に含めない
- テスト用の実データは、個人を特定できる情報（名前・ユーザー ID・スペース名・プロジェクト名）を架空の値に置き換える
