拡張案の検討

backlog-fix-review / backlog-review を、実際の請負のソフトウェア開発で便利に・有効に使うための拡張案。採用前の案を含む記録で、設計と作業の基準はあくまで plan.md・plan-review.md。

検討した日2026-10-17
対象の版20261013.1.0
プラン案にしたもの案 1・案 2（M15・M16 / R9・R10）

前提: いまのスキルが担っている範囲

1 つの PR の中で「指摘 → 解釈 → 修正とコミット → 返信 → 再レビュー → 解決」を確実に回すところまでは作り込まれている（ランクの規則、2 回の確認、秘密情報の検査、4 バイト文字の対策など）。請負の現場で効いてくるのはその外側で、次の 3 つに整理した。

  • 品質の記録: レビュー記録票・品質報告として、指摘と対応を後から示せること
  • 顧客との関係: 顧客のスペース・顧客のレビュアー・契約上の制約
  • 複数案件の並行: スペースや PR をまたいだ運用

優先度: 高（使い始めるとすぐ困るもの）

案 1

対応の記録の出力（レビュー記録票・品質データ）

高実装済み（未リリース）: plan.md §5-2 / M16・R10
困りごと
請負ではレビューの記録を品質記録や納品物として出すことが多い。いまは Backlog の画面とサマリーコメントでしか見られない。
案
「この PR のレビューの記録を出して」と頼むと（CLI の export <URL>）、指摘 1 件 = 1 行の CSV（Excel で開ける）と、集計つきの Markdown を .review-state/export/ に出力する。列は RC・指摘日時・指摘者・出どころ・重大度・分類・要約・場所・状態・対応内容・コミット・解決日時・解決者・往復の回数など。
設計の要点
  • Backlog のコメントから作り直す。状態ファイルがなくても、同じ PR なら同じ表になる
  • 読み取りだけ。出力先は固定し、任意のパスへは書かない
  • CSV の数式の注入（= などで始まるセル）・制御文字・秘密情報を処理する
  • 1 回に 1 つの PR。PR をまたいだ集計は、PR ごとの CSV を表計算ソフトでつなげて行う（PR の列を持つ）
決定
両方のスキルの CLI に入れる（7-11）、CSV と Markdown（7-12）。複数 PR の指定（7-13）は 1 回に 1 つの PR に決定（2026-10-17。スキルの利用の単位に合わないため）。列の並び（7-14）は plan.md §5-2 の列で固定に決定（2026-10-17。社内の記録票の様式には合わせない）。
案 2

指摘の分類（欠陥の種別）

高実装済み（未リリース）: plan.md §4-8 / M15・R9
困りごと
品質報告で求められるのは件数より「どんな種類の指摘が何件か」。いまは分類を持っていない。
案
指摘 1 件に分類を 1 つ（機能・ロジック、エラー処理、セキュリティ、性能、設計・保守性、規約・書式、テスト、ドキュメント、その他）。レビュー側は指摘の JSON の category、対応側は解釈の JSON の category で付ける。
設計の要点
  • マーカーには入れず、本文の決まった行（分類: / **分類**:）に書く。返信マーカーの正規表現は厳密で、項目を足すと以前の版が自動返信を新しい指摘と取り違えるため
  • ランク・返信の状態には使わない（表示と記録だけ）
  • 人間のレビュアーには書くことを求めない（ルールを増やさない）
決定
分類の一覧は既定の 9 分類で固定（7-10、2026-10-17。社内の欠陥分類には合わせない）。
案 3

複数の Backlog スペースの切り替え

高未着手
困りごと
顧客ごとに別のスペースに招待されることが多い。いまは BACKLOG_SPACE と BACKLOG_API_KEY が 1 組だけ。
案
  • (a) README に、direnv などでリポジトリごとに環境変数を切り替える運用を書く（コードの変更なし）
  • (b) スペースごとのキー（例: BACKLOG_API_KEY__<space>）を持てるようにする
注意
(b) はキーの送り先の制限（plan.md §6）に関わるので慎重に。まず (a) を推奨。
案 4

顧客のレビュアーへの配慮

高未着手
困りごと
必須のルール（RC-番号・RC-番号 ✅）を顧客に守ってもらえるとは限らず、守られないと「確認待ち」のまま残り続ける。返信の文面や「自動対応」の表示が顧客にどう映るかも気になる。
案
  • 長く fixed のままの指摘を、サマリーで目立たせる
  • 顧客がメールなど別の経路で了承したとき、利用者本人が理由を添えて解決にする手順を用意する
  • 返信の文体（敬語の度合い）を設定できるようにする
確認
顧客側のレビュアーが Backlog に直接コメントする運用かどうかで、優先度が変わる。

優先度: 中（効率と信頼性を上げるもの）

案 5

Backlog 課題（チケット）との連携

中未着手
案
PR に紐づく課題の説明・受け入れ条件を取得し、レビュー側では「要件どおりか」の観点に、対応側では意図の判定の材料に使う。
注意
新しく使う API（課題の取得）になるので、plan.md §2 の「使用する API」の更新が要る。課題へのコメントや状態の変更は外向きの操作なので、入れるなら別の確認を挟む。
案 6

自分の番の PR の一覧

中未着手
案
プロジェクトやリポジトリをまたいで、自分が関わる PR のうち返信待ち・確認待ちの指摘があるものを一覧にする（読み取りだけ）。複数の案件を並行するときに追いやすくする。
案 7

担当の引き継ぎ

中未着手
困りごと
いまは「1 つの PR は同じ人のアカウントでだけ対応する」前提（plan.md §4-6）。請負のチームでは担当の交代や休暇の代理が起こりうる。
案
引き継ぐ相手のユーザー ID を明示して、その人の返信マーカーも Bot の返信として読む。
注意
なりすましへの備えの前提を変えるので、需要が出てから検討する。

中未着手
案
PR の URL から、PR のブランチの worktree を作る手順を用意する。試験運用（M5）でも手作業だった。
案 11

サマリーを PR の説明文に置く

中実装済み（未リリース）: plan.md §4-5-1 / M17・R11
困りごと
サマリーはコメントなので、更新できるのは投稿した本人（対応側）だけ。レビュー側が解決を投稿しても、サマリーは対応側が次に動くまで古いまま。
案
PR の説明文の末尾に、印で囲んだ区画を置き、どちらのスキルからも更新する。更新できなければ、対応側だけが今までどおりコメントを使う（2026-10-17 に (c) で決定）。
注意
  • 作成者が書いた部分には触れない。印が壊れていたら止める
  • API に版の確認がないので、更新の直前に読み直して変わっていれば止める（短い時間の取りこぼしは受け入れる）
  • テスト用 PR で確かめること: 作成者以外が更新できるか、更新が変更の記録としてうるさく残らないか、HTML のコメントが見えないか、長さの上限、権限がないときのエラー

要確認（スキルだけでは解決できず、運用で決めること）

案 9

顧客のコードを LLM に送ってよいか

要確認未着手
困りごと
請負契約や秘密保持契約で、生成 AI の利用や外部への送信が制限されていることがある。
案
  • 使ってよいプロジェクトの許可リスト（プロジェクトキーの単位）を持ち、ほかの顧客で使う事故を防ぐ。いまは BACKLOG_SPACE でスペースを 1 つに限っているだけ
  • README に「契約上の確認」の注意を加える（安価で効果がある）
案 10

監査ログ

要確認案 1 に含められる
案
誰の承認で何を投稿し、何をコミットしたかの記録。状態ファイルの log にはすでに操作記録があるので、案 1 の出力に含められる。

派生案内容入れない理由・入れる条件
