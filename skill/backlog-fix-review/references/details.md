## できること・できないこと

| できること | できないこと（人が行う） |
|---|---|
| PR のコメントを全件読み、指摘ごとに状態（未対応・修正済み・解決など）を求める | 対応する指摘の最終的な選択（確認①） |
| 行コメントの場所をファイルの行番号に変換する | push と投稿の承認（確認②） |
| 場所と直し方がはっきりした指摘を修正し、指摘ごとにコミットする | 見送り（wontfix）の判断 |
| 回答・確認の質問・修正の報告を返信する | — |
| サマリーコメントを作成・更新する | — |

## 導入の補足

### 前提条件の細部

| 項目 | 内容 |
|---|---|
| git | `git diff --no-index` などが使えること |
| Backlog の API キー | キーは**あなたのすべての権限**を持つ |
| 対象リポジトリ | 手元に clone 済みで、`git fetch` / `git push` ができること。できない環境では、確認②の後にあなたが手で push と fetch をし、エージェントに続きを頼む |

### スキルの置き場所

フォルダ名は `backlog-fix-review` のままにしてください（スキルの名前と一致している必要があります）。`scripts/` の中の CLI はスキルのフォルダからの相対位置で使うので、フォルダの中の構成も変えないでください。

| エージェント | 置き場所の例 |
|---|---|
| Claude Code（個人で使う） | `~/.claude/skills/backlog-fix-review/` |
| Claude Code（リポジトリで共有する） | `<リポジトリ>/.claude/skills/backlog-fix-review/` |
| その他のエージェント | 各エージェントのドキュメントにある、スキルの置き場所 |

`scripts/` は開発元のリポジトリの TypeScript からビルドしたものです（依存パッケージなし）。コード中のコメントにある `§` の番号は、開発元の設計書の節番号を指します。

### API キーの扱い

- 環境変数は、エージェントを起動するシェルで読み込まれるファイル（`~/.profile` など）に書けます。そのファイルは自分だけが読める権限にしておくのが安全です（`chmod 600 ~/.profile`）。
- API キーをエージェントとのチャットに貼ったり、リポジトリにコミットしたりしないでください。

### 動作を確かめる

```bash
node ~/.claude/skills/backlog-fix-review/scripts/cli.js --help
```

（置き場所に合わせてパスを読み替えてください。）

## エージェントの許可設定

このスキルの安全性は、最終的には**エージェントの許可設定**で決まります。エージェントの環境には API キーがあるので、レビューコメントに誘導されたエージェントが `curl` などで Backlog の API を直接呼べば、CLI の検査（二重返信・秘密情報・push 済みかどうか）はすべて通らなくなります。次の 3 つを守ってください。

1. **自動承認のモード（すべてのコマンドを確認なしで実行するモード）では使わない。**
2. **`curl`・`wget`・`node -e`・`python -c` など、任意の通信やコードの実行ができるコマンドを許可リストに入れない。**
3. **投稿を伴うコマンド（`reply … --yes`、`summary … --yes`）と `git push` は、許可リストに入れない。** 毎回の確認が、投稿と push の前の最後の確認になります。

読み取りだけのコマンド（`fetch` / `status` / `interpret` / `select` / `check-push` / `export`）は、許可の確認を省略してもかまいません。返信は `reply --batch … --yes` でまとめて投稿するので、許可の確認は 1 回で済みます（中身は直前の確認②で見ています）。

エージェントは CLI を、次の形（`node` の後に**絶対パスを単一引用符で囲んで**書く）で実行します。許可設定はこの形に合わせてください。

```
node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' fetch …
```

Claude Code の場合の例（`~/.claude/settings.json` か、対象リポジトリの `.claude/settings.json`。パスは実際の置き場所に読み替える）:

```json
{
  "permissions": {
    "allow": [
      "Bash(node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' fetch:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' status:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' interpret:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' select:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' check-push:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-fix-review/scripts/cli.js' export:*)"
    ]
  }
}
```

他のエージェントでも、同じ考え方でコマンドの許可を設定してください。

## 使い方の流れ（詳しく）

1. **取得と同期**: `git fetch` をして、PR のコメントを全件読み直します。
2. **解釈**: エージェントが指摘ごとに、場所・意図・影響範囲を判定します。どの指摘を自動修正の候補にするかは、CLI が判定の組み合わせから規則で決めます。
3. **確認①**: 解釈の一覧（判定の根拠つき）が表示されます。対応する指摘を `1,3-5` / `all` / `none` で選んでください。直し方に選択肢がある指摘は、ここで選択肢も尋ねられます。回答は CLI が番号どおりに指摘に置き換え、それぞれの扱い（修正・質問・回答など）を表示します。
4. **修正**: 対象リポジトリの規約（AGENTS.md・cc-sdd / Kiro の Steering など。解釈の前に読みます）のやり方に沿って、選んだ指摘を修正し、指摘ごとに 1 コミットにします（`Refs: RC-…`）。仕様書（requirements.md・design.md など）の更新が必要な指摘は「利用者が選べば修正」として確認①に出るので、選んだ場合は仕様書も同じコミットで更新します。仕様書と Steering の場所は決め打ちせず、規約（AGENTS.md など）に書かれた場所に従います。書かれていなければ、既定の場所（`.kiro/specs/`・`.kiro/steering/`）を探します。使った場所とその根拠は確認①で表示されます。
5. **確認②**: コミット・**差分の全文**・push 前の検査（`check-push`）の結果・**検証の方法**・返信の下書きがすべて表示されます。差分は全文に目を通し、問題がなければ承認してください。
6. **push と投稿**: push した後、返信をまとめて投稿し（許可の確認は 1 回）、サマリーを更新します。

選ばなかった指摘は未対応のまま残ります。もう一度実行すると、前回の続きから対応できます（前回の解釈は、指摘が編集されたり新しい返信が付いたりしていなければ使い回されます）。

### 運用のこつ

- チームのレビュアーに [references/reviewer-guide.md](reviewer-guide.md) を共有してください。特に「返信は `RC-番号` で始める」「解決したら `RC-番号 ✅`（対応不要にするときは `RC-番号 ✅ 対応不要`）」の 2 つが大事です。サマリーコメントにも、状態ごとの「次にすること」と進み具合が表示されます。
- 自動対応の返信は、あなたのアカウントから「💻 自動対応」（本文では絵文字の記法 `:computer:`）と付けて投稿されます。Backlog のスペースによっては 4 バイトの文字（多くの絵文字）を投稿できないので、CLI は投稿する本文の 4 バイトの文字を `U+1F600` の形に置き換えます。
- **1 つの PR は、同じ人のアカウントでだけ対応してください。** 自動返信は「実行した人のアカウントで投稿され、最後の行に印があるもの」だけを自動返信とみなします。別の人が同じ PR で実行すると、前の担当者の自動返信が新しい指摘として扱われ、返信済みの指摘が未対応に戻り、サマリーも 2 つになります。担当の引き継ぎには対応していません。
- エージェントの環境で git の認証ができない場合は、確認②の後にあなたが手で push と fetch をし、エージェントに続きを頼んでください。

## 作成されるファイル

| 場所 | 内容 |
|---|---|
| `<対象リポジトリのルート>/.review-state/{PROJECT}-{repo}-pr{N}.json` | 状態ファイル。解釈の結果、指摘ごとのコミット、操作の記録 |
| `<対象リポジトリのルート>/.review-state/{PROJECT}-{repo}-pr{N}.snapshot.json` | 最後に同期した時点のコメントと状態（エージェントが読む） |
| `<対象リポジトリのルート>/.review-state/export/{PROJECT}-{repo}-pr{N}-{日時}.csv` と `.md` | `export` で出力した対応の記録。CSV は UTF-8（BOM 付き）で、Excel でそのまま開ける。Markdown は冒頭に集計（状態別・分類別など）。指摘者の名前とコメントの本文が入る。同じ名前のファイルがあれば上書きしない |

記録の列（CSV）: PR・RC・指摘日時・指摘者・出どころ（人間 / 自動レビュー）・重大度・分類・要約・本文（元のコメントの全文。CSV だけ）・場所・状態・対応区分（修正 / 回答 / 確認中 / 見送り）・対応内容・コミット・最終返信日時・解決日時・解決者・自動返信の回数・追加コメントの回数・リンク。PR の列があるので、PR ごとの CSV をつなげて集計できます。サマリーコメントと「指摘なし」のコメントは行にしません。`=` などで始まるセルは、表計算ソフトで数式として働かないよう先頭に `'` を付け、秘密情報らしき文字列のセルは省きます。

- worktree で実行した場合は、その worktree のルートに作られます。
- `.review-state/` は git に無視させていません（対応の記録として後で使えるようにするため）。スキルはこのフォルダをコミットしませんが、**手で `git add -A` などをするとコミットされる**ので注意してください。コメントの本文とレビュアーの名前が含まれます。API キーは含まれません。
- 正しい状態は常に Backlog のコメントにあります。`.review-state/` を消しても、次回の実行で作り直されます（解釈だけはやり直しになります）。

## セキュリティ上の注意

- **API キー**: 環境変数からだけ読みます。出力・エラーメッセージ・状態ファイルには書きません（URL 中のキーは `***` に置き換えます）。投稿する本文にキーや、秘密鍵・トークンらしき文字列があれば、投稿を中止します。キーは、そのままの形に加えて、よくある変形（区切り文字や空白を挟んだもの、URL エンコード、base64、16 進数、逆順、大文字・小文字の違い）も検出します。ただし**よくある形を見つけるためのもので、意図して変形したものをすべて見つけられるわけではありません**。リダイレクトはたどらず、API の呼び出しは 30 秒で打ち切ります。
- **API キーの送り先**: PR の URL のホストが `BACKLOG_SPACE` と一致しなければ中止します。
- **キーを外した実行**: 対象リポジトリのテスト・lint・`git commit`・`git push` は、`BACKLOG_API_KEY` を外した環境（`env -u BACKLOG_API_KEY`）で実行します。CLI が呼ぶ git にもキーを渡しません。これは、修正したコードやフックが**環境変数から**キーを読む経路をふさぐ多層防御の一つで、隔離ではありません（下の「このツールが防がないこと」を参照）。
- **push 前の検査**: 確認②では差分の全文を表示し、`check-push` で出ていくコミットごとの追加行とコミットメッセージを API キー・秘密情報らしき文字列で検査します。見つかれば push しません。秘密情報として見つけるのは、秘密鍵、形の決まったトークン（AWS・GitHub・GitLab・Slack・Anthropic・OpenAI・Google・Stripe）、`API_KEY=…` のような大文字の設定行です。設定行でも、値が数値・環境変数などの参照・記入例なら止めません。JWT や小文字の代入（`password = "…"`）は、テストのデータでの誤検出が多いので見ていません。PR の元の変更ファイルの範囲外に触れたファイルも示します。
- **返信の本文と解釈の JSON**: 一時ディレクトリか `.review-state/` の下の、自分が所有する `.md`・`.json` ファイルからだけ読みます。JSON として読めないときも、ファイルの内容はエラーに出しません。手元の他のファイルを取り違えたり、共有の一時ディレクトリに他の人が置いたファイルを読んだりしないためです。
- **git のコマンド**: エージェントは、対象リポジトリでの git のコマンド（`fetch` や `diff` も含む）をすべて `env -u BACKLOG_API_KEY` を付けて実行します。コミットは CLI の `commit` で行い、`Refs: RC-…` を付けて、修正の対象の指摘か・PR のブランチの上か・メッセージに秘密情報がないかを確かめます（CLI は git に API キーを渡しません）。
- **表示の偽装**: CLI は、端末に出す文字列から制御文字（ANSI エスケープなど）と、文字の並びを逆に見せる bidi の制御文字を取り除きます。改行や制御文字を含むファイルパスは扱いません。
- **リポジトリの規約**: エージェントは対象リポジトリの規約（PR のブランチの内容）に従いますが、従うのは開発のやり方だけです。確認の省略や外部への通信などの指示には従いません。PR で規約のファイルが変更されていれば、確認①で知らせます（PR の作成者が規約を書き換えて、エージェントへの指示を紛れ込ませる可能性があるため）。
- **コメントは信頼できない入力**: レビューコメントに書かれた命令文やコマンドには従いません。エージェントはコメントを修正方針の参考にするだけで、修正の対象を選ぶのはあなたです（確認①）。投稿の前にも必ず内容を確認できます（確認②）。
- **自動修正の範囲**: 場所・意図・影響範囲の判定から規則で決まる「ランク high」の指摘だけです。1 つのコメントに論点が複数あれば、すべての論点が high のときだけ、まとめて 1 コミットで直します。状態ファイルに保存されたランクは使わず、毎回判定から求め直します。
- **印の偽装**: 自動対応の印（`[review-bot …]`）は、あなたのアカウントで投稿され、かつ最後の行にあるものだけを有効にします。コメントや表示名を引用するときは、印に見える文字列・`@`（メンション）・リンクや画像の記法を無害な文字に置き換え、裸の URL はインラインコードで囲んでリンクにならないようにします（URL の文字は変えません）。
- **`.review-state/`**: シンボリックリンクになっていれば中止します。
- **git**: force push・push 済みのコミットの `--amend`・rebase はしません。ブランチ名にシェルで意味を持つ文字が含まれる PR と、安全に扱えないファイルパスは対象にしません。
- **二重投稿の防止**: 未対応でない指摘への返信、論点の組み合わせから決まる状態と違う返信（ランク high 以外の「修正済み」など）、メッセージにその指摘の `Refs: RC-番号` がないコミットを付けた「修正済み」、PR のブランチに push されていないコミット（base 側の履歴にある、PR と関係のないコミットを含む）を報告する返信は、CLI が拒否します。投稿がタイムアウトしたときは再試行しません。

### このツールが防がないこと

次のことは、運用で注意してください（設計の判断で対策していません）。

- **`.review-state/` の中身を信用しすぎない**: 対象リポジトリに `.review-state/` がコミットされていると、他の人が作った解釈が使われる可能性があります。確認①で、判定の根拠と「返信しない指摘」の一覧を必ず見てください。心当たりのない `.review-state/` がリポジトリにあれば、消してから実行してください。
- **`RC-番号 ✅` は誰でも書ける**: 他のレビュアーが指摘を解決済みにすることもできます。
- **対象リポジトリのコードは、あなたの権限で動く**: エージェントが修正したコードや、PR のブランチのテスト・git のフックは、あなたと同じユーザーで動きます。`env -u BACKLOG_API_KEY` を付けても、そのコードは `~/.profile` などの設定ファイルからキーを、`~/.ssh` やクラウドの設定からほかの資格情報を読めます。また `env -u` はキーを子のプロセスの環境から外すだけなので、同じユーザーで動くコードは、**キーを持ったままの親のプロセス**（エージェントやそのシェル）の環境を読めます（Linux の `/proc/<プロセス ID>/environ` など）。キーをファイルに置いても、同じユーザーのコードはそのファイルを読めるので、守れる範囲は変わりません。しかも修正後のテストは、確認②で差分を見る**前に**実行されます。エージェントはテストの前に自分の差分を見直しますが、コメントに誘導される可能性はゼロではありません。信頼できない人のコメントがある PR では、次のどれかを勧めます。
  - サンドボックスやコンテナ（資格情報を置いていない環境）でエージェントを動かす
  - API キーを `~/.profile` に書かず、エージェントを起動するシェルでだけ設定する（設定ファイルからは読まれなくなるが、上の親のプロセスの環境からは読めるので、サンドボックスの代わりにはならない）
  - テストの実行もエージェントの許可設定で毎回確認するようにし、実行の前に差分を見る

## CLI リファレンス

エージェントが内部で使うコマンドです。手で状況を確かめるときにも使えます。`--yes` を付けない限り、Backlog には何も投稿しません。

```bash
node <スキルのフォルダ>/scripts/cli.js status <PR の URL> --repo <対象リポジトリ>
```

| コマンド | 内容 |
|---|---|
| `fetch <URL>` | 同期して未対応の指摘を表示する |
| `status <URL>` | 同期してすべての指摘の状態を表示する |
| `interpret <URL> --file <json>` | 解釈を検証し、ランクを決めて、確認①の一覧を表示する |
| `commit <URL> --key <RC-…> --message-file <txt>` | ステージした変更を、指摘 1 件の修正としてコミットする（`Refs: RC-…` を付け、修正の対象か・PR のブランチの上か・秘密情報がないかを確かめる） |
| `select <URL> --choice <1,3-5 / all / none>` | 確認①の回答を、指摘の番号と扱い（修正・質問・回答・見送り）に置き換えて表示する |
| `reply <URL> --batch <json> [--yes]` | 複数の返信をまとめて扱う（`--yes` がなければ下書きの表示だけ）。JSON は `[{"key", "status", "bodyFile", "commits"}]` の配列 |
| `reply <URL> --key <RC-…> --status <状態> --body-file <md> [--commit <sha>]... [--yes]` | 1 件だけ返信する（`--yes` がなければ下書きの表示だけ） |
| `summary <URL> [--yes]` | サマリーを作成・更新する（`--yes` がなければ下書きの表示だけ） |
| `check-push <URL>` | push する差分の追加行とコミットメッセージを API キー・秘密情報で検査する（見つかれば終了コード 1）。PR の元の変更ファイルの範囲外のファイルも示す |
| `export <URL> [--all]` | 指摘ごとの対応の記録を CSV と Markdown にして `.review-state/export/` に出力する（読み取りだけ。出力先は変えられない）。`--all` で返信しない指摘も出す。状態ファイルがあれば、まだ返信していない指摘の分類と、返信しない指摘の判定を補う |

共通オプション: `--repo <dir>`（対象リポジトリ。既定はカレントディレクトリ）

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| `環境変数 BACKLOG_API_KEY（または BACKLOG_SPACE）が設定されていません` | README の導入の手順 2 を行い、エージェントを起動し直す |
| `ホスト … が BACKLOG_SPACE と一致しません` | URL のスペースと `BACKLOG_SPACE` が合っているか確かめる |
| `origin/… が対象リポジトリにありません` / `blob … が手元のリポジトリにありません` | 対象リポジトリで `git fetch origin` を実行する |
| `git fetch` / `git push` が認証エラーになる | git の認証（credential helper か SSH 鍵）を設定する。設定できない環境では、あなたが手で push と fetch をする |
| `状態ファイルは別のユーザーで作られています` | 別の人の `.review-state/` が残っている、または別のアカウントの API キーで実行した。自分の API キーか確かめる。別の人が対応してきた PR なら、引き継ぎには対応していないので、その人に続けてもらう |
| `… はすでに fixed です。返信しません` | すでに返信済み。二重投稿を防ぐための動作 |
| `ブランチ名に使えない文字が含まれている` | 安全のため対象外。ブランチ名を英数字と `._+/-` だけにする |
| `返信の本文は、一時ディレクトリか .review-state/ の下の .md ファイルにしてください` | 本文の置き場所の制限。エージェントに置き場所を直してもらう |
| 行コメントの場所が「位置不明」 | 指摘の後にファイルが大きく変わったか、blob が手元にない。`git fetch` を試し、だめならエージェントが本文から場所を推定する |
| `push を中止してください: … らしき文字列があります` | `check-push` が差分かコミットメッセージに秘密情報らしき文字列を見つけた。差分を見て、本当に秘密情報なら修正を取り消す。誤検出なら、その行を書き換えるか、利用者の判断で手で push する |
| `… 秒以内に応答がありませんでした。投稿されたか分からないため …` | 投稿が届いたか分からない。`status` で状態を確かめ、まだ `open` なら再実行する（すでに返信済みなら、CLI が二重投稿を拒否する） |
| `返信の本文のファイルが、自分の所有するファイルではありません` | 共有の一時ディレクトリに、他の人が置いたファイルがある。`mktemp -d` で作った自分専用のディレクトリに本文を書き直す |
| `node: command not found` / 構文エラー | Node.js 20 以上を入れる |
