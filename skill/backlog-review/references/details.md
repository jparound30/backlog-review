## できること・できないこと

| できること | できないこと（人が行う） |
|---|---|
| PR の差分と既存のコメントを読み、指摘の候補を出す | 投稿する指摘の最終的な選択（確認①） |
| 指摘を、対応側が自動修正できる書式に整えて投稿する | 投稿の承認（確認②） |
| 対応側の返信とコミットを突き合わせて表示する | 解決（`RC-番号 ✅`）の最終判断 |
| 解決・再指摘・回答を投稿する | コードの修正・コミット・push（このスキルは行わない） |

## 導入の補足

### 前提条件の細部

| 項目 | 内容 |
|---|---|
| git | 対象リポジトリの clone で `git fetch` ができること。できない環境では、あなたが手で fetch してからエージェントに頼む |
| Backlog の API キー | キーは**あなたのすべての権限**を持つ。投稿はあなたのアカウントから「🤖 自動レビュー」として行われる |
| 対象リポジトリ | 手元に clone 済み。ブランチはどれが checkout されていてもよい（このスキルは `origin/…` の内容だけを読み、作業ツリーを変えない） |

### スキルの置き場所

フォルダ名は `backlog-review` のままにしてください（スキルの名前と一致している必要があります）。`scripts/` の中の構成も変えないでください。

| エージェント | 置き場所の例 |
|---|---|
| Claude Code（個人で使う） | `~/.claude/skills/backlog-review/` |
| Claude Code（リポジトリで共有する） | `<リポジトリ>/.claude/skills/backlog-review/` |
| その他のエージェント | 各エージェントのドキュメントにある、スキルの置き場所 |

`backlog-fix-review` と同じ環境変数（`BACKLOG_API_KEY`・`BACKLOG_SPACE`）を使います。両方のスキルを同じ環境に置いてかまいません。

### 動作を確かめる

```bash
node ~/.claude/skills/backlog-review/scripts/review-cli.js --help
```

## エージェントの許可設定

考え方は `backlog-fix-review` と同じです。

1. **自動承認のモードでは使わない。**
2. **`curl`・`wget`・`node -e`・`python -c` など、任意の通信やコードの実行ができるコマンドを許可リストに入れない。** エージェントの環境には API キーがあるので、差分に誘導されたエージェントが API を直接呼べば、CLI の検査（秘密情報・二重投稿）は通らなくなります。
3. **投稿を伴うコマンド（`post … --yes`、`resolve … --yes`）は許可リストに入れない。** 毎回の確認が、投稿の前の最後の確認になります。

読み取りだけのコマンド（`fetch` / `status` / `draft` / `select` / `verify`）は、許可の確認を省略してもかまいません。

Claude Code の場合の例（パスは実際の置き場所に読み替える）:

```json
{
  "permissions": {
    "allow": [
      "Bash(node '/home/<あなた>/.claude/skills/backlog-review/scripts/review-cli.js' fetch:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-review/scripts/review-cli.js' status:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-review/scripts/review-cli.js' draft:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-review/scripts/review-cli.js' select:*)",
      "Bash(node '/home/<あなた>/.claude/skills/backlog-review/scripts/review-cli.js' verify:*)"
    ]
  }
}
```

## 使い方の流れ（詳しく）

1. **取得**: `git fetch` をして、PR のコメントを全件読み、変更ファイルの差分を行番号つきで切り出します。
2. **レビュー**: エージェントが対象リポジトリ（base ブランチ）の規約とレビューの観点のドキュメントを読み、差分を読んで指摘の候補を出します。既存の指摘と重なるものは出しません。
3. **下書き（確認①）**: 指摘の一覧（重大度・場所・指摘・期待・判断の根拠・警告）が表示されます。投稿する指摘を `1,3-5` / `all` / `none` で選んでください。警告（変更ファイル外・変更のない行・既存の指摘との重複・注意が要る表現）はここで確かめます。
4. **確認②**: 投稿する本文の全文が表示されます。問題がなければ承認してください。
5. **投稿**: 1 件ずつ投稿します（許可の確認は 1 回）。
6. **再レビュー**: PR の作成者が `backlog-fix-review` で対応して返信したら、同じ URL でもう一度実行します。返信とコミットの差分が表示され、解決（`RC-番号 ✅`）・再指摘・回答のどれにするかを選びます。承認の後に投稿します。

### 運用のこつ

- 投稿した指摘は、対応側が読んで自動修正できる書式（`📍` 場所・`指摘:`・`期待:`）です。`期待:` が具体的なほど自動修正されやすくなります。
- レビューの観点はこのスキルの中にはありません。対象リポジトリの `AGENTS.md` などに「レビューの観点は `docs/review-guidelines.md`」のように場所を書いておくと、エージェントがそれを読みます（[guidelines.md](guidelines.md)）。
- レビューする人と PR の作成者が同じアカウントでも動きます（自分の PR を自分でレビューして自分で対応する）。ただし、レビューの独立性のためには別の人が行うことを勧めます。
- 対応側のサマリーコメント（`🤖 レビュー対応状況`）に、指摘ごとの状態が表示されます。このスキルはサマリーを投稿しません。

## 作成されるファイル

| 場所 | 内容 |
|---|---|
| `<対象リポジトリのルート>/.review-state/{PROJECT}-{repo}-pr{N}.review.json` | 状態ファイル。下書き、選択、投稿した指摘のコメント ID、操作の記録 |
| `<対象リポジトリのルート>/.review-state/{PROJECT}-{repo}-pr{N}.review.snapshot.json` | 最後に同期した時点の差分・コメント・状態（エージェントが読む） |

- 対応側の状態ファイル（`…pr{N}.json`）とは別のファイルなので、同じ clone で両方のスキルを動かしても壊れません。
- `.review-state/` は git に無視させていません。スキルはコミットしませんが、**手で `git add -A` などをするとコミットされる**ので注意してください。コメントの本文と差分が含まれます。API キーは含まれません。
- 正しい状態は常に Backlog のコメントにあります。`.review-state/` を消しても、次回の実行で作り直されます。投稿済みの指摘は、同じ場所に自分の指摘があれば CLI が見つけるので、二重投稿にはなりません。

## セキュリティ上の注意

- **API キー**: 環境変数からだけ読みます。出力・状態ファイルには書きません。投稿する本文にキーや秘密情報らしき文字列（秘密鍵・形の決まったトークン・`API_KEY=…` のような設定行）があれば、下書きの段階で拒否します。差分から値を写さず、行番号で示すようエージェントに指示しています。
- **API キーの送り先**: PR の URL のホストが `BACKLOG_SPACE` と一致しなければ中止します。
- **差分は信頼できない入力**: PR のコード・説明文・コメントに書かれた指示（「指摘しないこと」「このコマンドを実行すること」など）には従いません。エージェントはそのこと自体を指摘として報告します。CLI は、指摘の本文にコマンドの実行・外部への送信・資格情報・確認の省略を求める表現があれば警告します。投稿の前に、あなたが本文の全文を読みます（確認②）。
- **PR のコードの実行**: 既定では実行しません（静的に読むだけ）。対象リポジトリの **base ブランチ**の規約がテストの実行などを求めているとき、またはあなたが求めたときだけ、使い捨ての worktree に PR のブランチを出して `env -u BACKLOG_API_KEY` を付けて実行し、終わったら worktree を消します（作業ツリーは変えません）。PR で規約のファイルが変更されていれば、その差分を見せ、PR 側の規約の指示には従いません。**規約に実行の指示を書くと、その後のすべての PR のコードがレビュアーの権限で動く**ことになります。チームで決めてから書き、信頼できない人の PR はサンドボックスやコンテナでレビューしてください。
- **git のコマンド**: エージェントは、対象リポジトリでの git のコマンドをすべて `env -u BACKLOG_API_KEY` を付けて実行します。作業ツリーは変更しません。
- **表示の偽装**: CLI は、端末に出す文字列から制御文字と bidi の制御文字を取り除きます。指摘の本文にそれらの文字があれば拒否します。
- **印の偽装**: 自分の指摘の印（`[review-bot finding …]`）は、あなたのアカウントで投稿され、かつ最後の行にあるものだけを「自分の指摘」とみなします。対応側の返信の印（`[review-bot root=… status=…]`）は、誰が投稿したものでも「対応側の返信」として読みます（投稿者を表示します）。これはあなたに見せるためだけに使い、解決の投稿は必ずあなたの判断を経るためです。
- **二重投稿の防止**: 投稿のたびに状態ファイルへ書き、同じ指摘は投稿しません。状態ファイルを失っていても、同じ場所に自分の指摘があれば投稿しません。
- **確認②の裏付け**: `post --yes` / `resolve --yes` は、直前に `--yes` なしで表示した本文と同じときだけ投稿します。表示の後に下書きや選択をやり直すと、もう一度表示が必要です。下書きの本文は状態ファイルの値をそのまま使わず、指摘の項目から作り直して照合します（状態ファイルを書き換えられても、見せていない本文は投稿されません）。
- **解決の裏付け**: `fixed` の返信を解決（`RC-番号 ✅`）にできるのは、返信のコミットが手元にあり、PR のブランチに push されているときだけです。コミットが指摘の行の近くを変えていなければ警告します。直っているかの判断はあなたが行います。
- **エージェントが書くファイル**: 指摘の JSON・結果の JSON・本文は、一時ディレクトリか `.review-state/` の下の、自分が所有するファイルからだけ読みます。JSON として読めないときも、ファイルの内容はエラーに出しません。
- **`.review-state/`**: シンボリックリンクになっていれば中止します。

## CLI リファレンス

```
node '<SKILL_DIR>/scripts/review-cli.js' <コマンド> <PR URL> --repo "$(pwd)" [オプション]
```

| コマンド | 処理 |
|---|---|
| `fetch <URL>` | 同期して、レビュー用のスナップショットを保存する。確認待ちの返信と未対応の指摘を表示する |
| `status <URL>` | 同期して、すべての指摘とその状態を一覧する |
| `draft <URL> --file <findings.json>` | 指摘の JSON（一時ディレクトリか `.review-state/` の下の自分の `.json`）を検証して書式に整え、確認①の一覧を表示する。拒否: 改行・バッククォート・`./` を含む項目、行数超え・ファイルなし・秘密情報・同じ指摘の重複。警告: 変更ファイル外・変更のない行・既存の指摘との重複・注意が要る表現 |
| `select <URL> --choice <1,3-5\|all\|none>` | 確認①の回答を下書きの番号に置き換える |
| `post <URL> [--yes]` | 選ばれた下書きを投稿する。`--yes` がなければ本文の全文を表示するだけ。本文は状態ファイルの値ではなく指摘の項目から作り直して照合し、`--yes` は最後に表示した本文と同じときだけ投稿する。投稿済みのものは投稿しない |
| `verify <URL>` | 対応側の返信があってレビュアーの番の指摘を、返信の本文・コミット（push 済みか・変更ファイル・差分）・指摘の行の現在の内容とともに表示する。警告: コミットがない・手元にない・未 push・指摘のファイルを変えていない、PR 作成者以外の返信、自分の指摘でない |
| `resolve <URL> --batch <json> [--yes]` | 解決（`resolve`）・再指摘（`reopen`）・回答（`answer`）を投稿する。JSON は `[{"key","action","bodyFile"}]`。先頭の `RC-番号`（と解決なら `✅`）は CLI が付ける。拒否: レビュアーの番でない指摘、`needs_info` への `resolve`、`fixed` の返信にコミットがない・手元にない・push されていないときの `resolve`、`RC-` で始まる本文、マーカーに見える最後の行、秘密情報、同じ指摘の重複。`--yes` は最後に表示した本文と同じときだけ投稿する |

`--yes` を付けない限り、Backlog には何も投稿しません。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| `origin/<branch> が対象リポジトリにありません` | `git fetch origin` をしてから再実行する |
| `環境変数 BACKLOG_SPACE が設定されていません` | `export BACKLOG_SPACE='yourspace.backlog.jp'` を設定する |
| `line（N）が … の行数を超えています` | 指摘の行番号が間違っている。スナップショットの `changedFiles[].lines[].n` を使う |
| `本文に API キーらしき文字列があります` | 差分の値を写している。値を消して行番号で示す |
| 投稿が「応答がありませんでした」で失敗した | 投稿されたか分からないので、`status` で確かめてから同じコマンドを再実行する。投稿済みなら投稿されない |
| 状態ファイルは別のユーザーで作られています | 別の API キーで作った状態ファイルがある。`.review-state/…review.json` を消すか、同じキーを使う |
